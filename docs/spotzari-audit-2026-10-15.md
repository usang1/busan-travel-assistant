## 검증

- 실제 사이트: 한국어 홈·장소·지도·로그인·입점·업주·관리자, 영어 홈 확인. 이미지 깨짐과 JS 예외는 해당 순회에서 발견하지 못했다. 운영 모바일 홈 H1 중복 및 업주 화면 H1/metadata 누락을 재현했다.
- 운영 API: 관리자 조회 2개, 업주 조회 1개, 인증 없는 관리자/업주/가입 설정 POST 3개 모두 401. 빈 요청은 인증 단계에서 거절되었으며 데이터 쓰기는 수행하지 않았다.

- 공개 데이터 경계 검사: 정상 조회 및 3단계 호환 fallback 전체에서 내부값 제거, 관리자 데이터 유지, 업주 ID 조건 유지, 원본 데이터 불변성.

## 추가 승인 또는 운영 환경 검증이 필요한 사항

1. **DB 권한 분리 (높음, 승인 필요).** 연결된 Supabase에 익명 키로 검수자/검수 메모 컬럼 조회가 가능함을 확인했다(샘플 값은 null; 실제 개인정보 유출 여부는 확인하지 않음). 웹 응답 redaction만으로 직접 DB API 조회는 차단할 수 없다. 공개 전용 컬럼/뷰 또는 관리자 전용 테이블과 권한을 설계하고 기존 RLS/관리자/업주 호환성을 검증한 뒤 승인받아 적용해야 한다. 이번 작업에서는 SQL을 적용하지 않았다.
2. **DB와 migration 정합성 (높음, 승인 필요).** `admin_summary` 단독 조회가 PostgreSQL `42703`(컬럼 없음)을 반환했다. 저장소 migration 015 및 관리자 폼과 실제 DB가 다를 수 있다. migration 이력/백업을 확인한 뒤 필요한 변경만 승인받아 적용해야 한다.
3. **공개 GPT 번역 비용 제한 (높음).** `/api/translate-to-korean`에는 입력 길이 제한은 있으나 코드상 분산 rate limit이 없다. 운영 WAF/게이트웨이 제한 여부는 확인하지 못했다. 비로그인 번역을 유지하면서 요청량·동시성·비용 상한을 정할 필요가 있다.
4. **실제 역할 계정 통합 QA.** 관리자·승인 업주·일반 사용자 실계정으로 승인/반려/소유 업체 수정/타 사용자 데이터 접근을 검증해야 한다. 이번에는 운영 데이터를 변경하지 않고 서버 권한 테스트와 모의 브라우저 세션을 사용했다. 실제 RLS 전체와 OAuth 공급자 설정은 검증 완료로 간주하지 않는다.
5. **실사용 성능.** 중복 데이터 제거, 소유 업체 쿼리 축소, 편집기 지연 로딩과 랜딩 이미지/렌더링 최적화를 적용했다. Lighthouse 수치는 로컬 프로덕션 빌드의 모의 모바일 네트워크 결과다. 배포 후 실제 기기/네트워크의 LCP·INP·CLS 및 지역별 TTFB를 측정해야 한다.
6. **콘텐츠 완성도.** 운영 홈에서 부산 23·서울 2·제주 2 공개 장소, 완전 검수 0을 확인했다. 검수 완료 장소와 언어별 콘텐츠를 늘리는 운영 작업이 필요하다. 검수 표시·추천 점수는 임의로 바꾸지 않았다.

## 2026-10-16 후속 구현: 자동 수집·3단계 검증·성장 기반

- 현재 위치 실패 원인은 단일 요소가 아니라 Naver SDK 중복 로딩 경합, 실패 Promise 영구 캐시, 브라우저 권한/HTTPS 오류의 단일 메시지 처리, 서버 지오코딩 대체 경로 부재가 겹친 구조였다. 공통 SDK 로더, 오류 코드가 있는 Geolocation 래퍼, 서버측 Kakao 지오코딩·역지오코딩, 지도 클릭 위치 선택으로 분리했다.
- Google Places·Kakao·Naver 공식 검색을 서버 라우트로 통합했다. 키는 서버 환경변수만 사용하고, 타임아웃·요청 제한·단기 캐시·정규화·수동 입력 fallback을 적용했다. 로컬 환경에서는 Naver 지도 공개 키만 설정되어 있으며 장소 검색용 Naver/Kakao/Google 키는 없어 실제 제공자 응답은 검증하지 못했다.
- `053_place_field_verification_system.sql`에 자동 수집, 온라인·사업자 확인, 현장 확인을 필드별로 저장하는 데이터 출처·검증·방문·사진·변경 이력·점검 주기·CSV batch/row 구조와 RLS를 추가했다. 기존 장소는 자동으로 검증 승격하지 않는다. 실제 방문 행과 연결되지 않은 `field_verified`는 DB trigger로 거절한다.
- 기존 공식·현장 검증값과 새 API/CSV/사업자 값이 다르면 검증값을 보존하고 `has_conflict`와 제안값을 별도로 기록한다. 사용자 화면은 관리자 승인, 공개 허용, 비충돌 조건을 모두 만족하는 항목만 표시한다.
